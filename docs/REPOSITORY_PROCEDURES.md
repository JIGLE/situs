# Repository procedures

**This file is authoritative for how work reaches `main`** — branching, pull requests,
Dependabot, releases, and the start/finish routine every session follows. `CONTRIBUTING.md`,
`CLAUDE.md` and `.github/BRANCH_PROTECTION.md` defer to it and keep only their own concerns.

It exists because three documents once described three different branching models and the actual
practice matched none of them. Two of the claims were not merely stale but false: merged branches
were documented as auto-deleted while two release branches sat un-deleted on the remote, and
`CLAUDE.md` pointed every AI session at a branch 47 commits behind `main`. The repository already
knows this failure mode — hygiene rule 3 in `CLAUDE.md` calls a stated fact a claim with an
expiry — but the rule had only ever been applied to product documentation, never to process.

Applies equally to humans and to AI coding sessions. Where a rule exists because an AI session
got it wrong, that is said plainly rather than generalised.

---

## 1. Branching

Trunk-based. `main` is the only long-lived branch. There is no `develop`.

| Prefix           | For                         | Example                    |
| ---------------- | --------------------------- | -------------------------- |
| `feat/<desc>`    | New capability              | `feat/lease-expiry-alerts` |
| `fix/<desc>`     | Bug fix                     | `fix/unused-nav-helper`    |
| `chore/<desc>`   | Maintenance, CI, docs, deps | `chore/upgrade-prisma-7`   |
| `hotfix/<desc>`  | Critical patch on live code | `hotfix/auth-token-leak`   |
| `release/vX.Y.Z` | Generated by `release.yml`  | `release/v1.25.0`          |
| `dependabot/**`  | Generated by Dependabot     | —                          |

`scripts/check-branch-name.js` enforces this and runs inside `npm run hygiene`.

**A branch is per-change, not per-session.** This is the rule the old arrangement broke. A branch
named after a session or a person accumulates unrelated work, outlives the PR that merged it, and
ends up carrying commits nobody can review as a unit. Branch from `origin/main`, do one change,
open one PR, let it merge, delete the branch, branch again.

## 2. A merged pull request is finished

Once a PR merges it cannot track new work. Never push new commits onto a branch whose PR has
merged: reviewers see a closed PR, and the commits belong to no reviewable unit.

```bash
git fetch origin main
git checkout -B <new-branch-name> origin/main
```

If the branch already carries unmerged commits beyond the merged history, keep them — rebase onto
the new base rather than discarding.

**After merging, check that the head branch is gone, and delete it if it is not.** Do not rely
on the repository setting in either direction. Merging #386 on 2026-09-22 deleted its head branch
automatically; `release/v1.24.0` and `release/v1.25.0` were not deleted when #319 and #362 merged.
`git ls-remote --heads origin <branch>` answers it for the branch in front of you, and the sweep
in §6 answers it for all of them.

## 3. Pull requests

1. Branch from current `origin/main`.
2. Push and open a PR against `main`.
3. All required checks green. The exact names are:
   - `verify / Lint & Type Check`
   - `verify / Unit Tests`
   - `Build validation`
   - `Dependency Security Scan`

   The `verify / ` prefix is load-bearing. `ci.yml`'s `verify:` job calls `reusable-verify.yml`
   via `uses:`, and GitHub prefixes reusable-workflow job names with the calling job's name. A
   required check is matched by exact string, so the bare names `Lint & Type Check` and
   `Unit Tests` match nothing and sit "Expected — waiting…" forever. That happened, and only an
   admin merge got anything through (found on PR #301). If `reusable-verify.yml`'s job names or
   `ci.yml`'s calling job id change, update `.github/branch-protection-config.json` in the same
   commit.

4. Merge, then confirm the head branch is gone (§2).

**Do not open a pull request unless it was asked for.** An unrequested PR is a review request
somebody now has to decline.

## 4. Dependabot

**Never push a commit onto a `dependabot/*` branch.** Dependabot treats external commits on its
own branches as interference and can close the PR in response. That happened to PR #276: a fix
pushed to its branch got the PR silently closed and its branch desynced from GitHub's own PR and
CI views, although the git ref itself was correct.

To fix a bump that needs one, recreate the same version changes plus the fix on `chore/deps-<group>`,
verify, and open a new PR. Let the original close on its own once superseded.

**Grouping.** `.github/dependabot.yml` groups bumps so a weekly run produces few, reviewable PRs.
One group deserves explanation: a `major-updates` group matching `patterns: ["*"]` puts every
major bump of the week into a single PR, where one incompatible package blocks every other. PR
#384 is the worked example — it moved TypeScript to 7.0.2 while `@typescript-eslint/eslint-plugin`
declared `peer typescript@">=4.8.4 <6.1.0"`, so `npm ci` failed with ERESOLVE and all five jobs
died within ten seconds, taking nine unrelated and perfectly fine bumps down with it.

The fix is to group by what constrains what: TypeScript travels with the eslint toolchain that
pins its range, and everything else bumps independently. When a group fails to resolve, read the
`npm error` block rather than re-running — ERESOLVE names the conflicting peer exactly.

## 5. Releases

Nothing publishes on merge. The chain is:

1. Dispatch `release.yml` — it bumps versions on `release/vX.Y.Z` and opens a PR.
2. Merge that PR — `publish` tags the commit.
3. The tag push triggers `deploy-ghcr.yml`.

Only a tag push may write `:latest` or a bare `:<version>`; a manual deploy dispatch publishes
`sha-<short>`. The release workflow squash-merges its own PR and depends on `enforce_admins:
false`; turning that on requires giving the workflow a fine-grained PAT or a GitHub App with
bypass rights first. See `.github/BRANCH_PROTECTION.md`.

Release PRs are squash-merged, so a release branch never becomes an ancestor of `main` and
`git branch --merged` never lists one. The sweep in §6 compares patches instead, which finds them.

## 6. Session procedure

### Starting

```bash
git fetch origin --prune
git status                      # clean tree?
git log --oneline -1 origin/main
git rev-list --count origin/main..HEAD   # commits ahead
git rev-list --count HEAD..origin/main   # commits behind — should be 0
```

Confirm three things before writing code: the branch name fits §1, the branch is based on current
`origin/main`, and no merged PR already owns it (§2). `gh`/`hub` are not available in AI sessions —
use the GitHub MCP tools.

### Finishing

Run the full gate and **read the exit code**, not a grep of the output:

```bash
npm run verify:ci    # type-check → lint → format:check → hygiene → security:audit → test
```

One result is known and expected. It is not caused by your change and should not be
re-diagnosed each session: **three DB-backed integration suites fail locally** — `pii-extension`,
`bank-connection`, `product-events` — because Prisma's agent guard blocks `prisma db push` under an
AI session. They run in CI. **Never set `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`.**

`security:audit` has no expected failure. If it reports an advisory, check whether clean `main`
reports it too; either way it gets fixed rather than waived — through an `overrides` entry in
`package.json` when no upgrade exists.

Then commit, push with `git push -u origin <branch>`, and report what you verified rather than
what you assumed. Count tests from the run output; a figure written from memory went into a
commit message and had to be amended before the push.

### Branch hygiene sweep

```bash
git fetch origin --prune
for b in $(git for-each-ref --format='%(refname:lstrip=3)' refs/remotes/origin); do
  case "$b" in main|HEAD|gh-pages|dependabot/*) continue ;; esac
  if [ -z "$(git cherry origin/main "origin/$b" | grep '^+')" ]; then echo "merged: $b"; fi
done
```

A branch is listed when every one of its commits already has an equivalent patch on `main`, so
merge-commit, rebase and single-commit squash merges are all caught. Anything listed can be
deleted. It skips `gh-pages`, the Pages publish target and permanently divergent by design, and
`dependabot/*`, which Dependabot owns (§4).

It replaced `git branch -r --merged origin/main`, which only sees branches that are ancestors of
`main`. Release PRs are squash-merged, so that command printed nothing while `release/v1.24.0`
and `release/v1.25.0` sat on the remote for weeks — a sweep that reported clean on exactly the
case it existed for.

**One blind spot, stated so it is not mistaken for coverage:** a branch of _several_ commits that
was squash-merged still shows as unmerged here, because the single squash commit matches none of
its individual patches. For those, the pull request's merged state is the source of truth.

## 7. Never

- Push directly to `main`.
- Push to a `dependabot/*` branch (§4).
- Set `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`.
- Open a pull request that was not asked for.
- Raise a ratchet's baseline to make a checker pass. `css:check`, the coverage thresholds and
  `lint:colors` are ratchets: they exist to fail when something regresses. Fix the regression.
- Rewrite history on a branch somebody else may have checked out — no rebase, amend or
  force-push. A merge commit keeps their checkout valid.
- Leave a document asserting something the commit just made false. Rewrite it in the same commit,
  and add the old wording to `RETIRED_CLAIMS` in `scripts/check-docs.js` so it cannot return.
