### Scope cutdown (2026-09, complete)

The product was judged overscoped — too much surface to maintain, too much for a new landlord
to face, and too slow to a first shippable version. It is pre-launch with no users, so the work
is pure subtraction: keep the core loop (bank movement → match → allocate → receipt → tax filing
→ audit trail) and the compliance substrate around it, and delete the rest rather than hide it
behind a flag. Git history is the archive.

| 3     | Intelligence / Analytics / Reports / Insights                                        |
| 4     | Admin user directory, instance metrics, database ops endpoint                        |

### Completed Features

- **Authentication**: NextAuth v4 with Google OAuth + credentials provider, CSRF protection, session-based auth
- **CRUD Operations**: Full create/read/update/delete for Properties, Units, Buildings, Tenants, Owners, Leases, Receipts and Expenses
- **Portfolio View**: Compact action-driven layout with IssueAlert zone, List/Map tabs, Next Action column, attention row highlights
- **Tenant Detail Modal**: 4-zone decision-driven interface (Status+Health / Primary Action / Issues Panel / Tabbed info); property and building detail open over any page as `?detail=<type>:<id>`
- **Property Map**: Status-coded divIcon markers with legend, slide-in side panel, FitBoundsController, dynamic viewport height
- **Financials**: 4-tab container (Action Queue / Receipts / Occupancy & Rent / Tax Summary) — all 4 fully wired; standardized expense categories
- **Buildings**: Building entity in AppState+context; CRUD API; BuildingsView at `/buildings`; nav entry
- **Portfolio Building Grouping**: Property list uses canonical Building entity for group headers (grid + table); table view inserts section header rows for multi-unit groups
- **Email Integration**: SMTP with templates, bulk sending, delivery tracking, exponential-backoff retry
- **Monitoring**: Health endpoints (owner-gated), Prometheus-compatible `/api/metrics`
- **Compliance**: GDPR audit logging, Iberian tax compliance (PT/ES), admin data-access audit trail
- **Internationalization**: next-intl with PT, EN, ES, IT locale support
- **Testing**: Vitest unit/integration suite (line coverage enforced as a ratchet in `vitest.config.ts`), Playwright E2E suite, CI quality gates (`--max-warnings=0`)
- **Security**: CSP with nonces, input sanitization, rate limiting, timing-safe auth comparisons
- **Infrastructure**: Dockerized for TrueNAS SCALE, standalone Next.js output, SQLite
- **Admin**: the instance's status, and Access: who may create an account (invitations, or Google sign-up as a manager), who has one, and its role

| 2026-10-09 | The audit-log retention copy says what the schema does                                                                                              | Settings and the privacy page said audit logs are kept 7 years "(legal obligation)", and the Article 30 record gave the reason as fiscal and legal record-keeping, while `AuditLog.userId` cascades: erasing an account erased its entries. | 2026-10-09 | The middleware rate limiter counts a request atomically, and keeps limiting when Redis is down                                                      | `rateLimit` read an entry, added one in its own memory and wrote it back: exact in one process, but with Redis a parallel burst all read the same count and all passed (found in the audit of the 2FA-disable route). The store now has one `hit(key, windowMs)`: a Lua script in Redis (`INCR`, expiry when none, count and time left), the same in memory. | 2026-10-08 | IBAN hashes are keyed with the PII key, so the database file alone cannot be hashed back to IBANs                                                   | `hashIban` was a plain SHA-256, and a Portuguese IBAN has about a billion candidates per bank and branch: anyone with the file could read the numbers back, which undid the AES encryption on `iban`. The movement fingerprint embeds the hash, so it is rebuilt too, but only after the old one is reproduced from the row and found equal. | 2026-10-08 | Erasing an account removes what its rows do not take with them: email log rows, bank consents, stored files                                         | The earlier claim that erasure was complete by cascade was not true: `EmailLog` is `SetNull`, so its recipient addresses outlived the account for up to two years; a PSD2 consent stayed live at the bank until it lapsed; the receipt archives (a tenant's name, address and amount) stayed on disk, since nothing in the app removed a stored file. `deleteOwnAccount` now deletes the log rows in the same transaction as the account (a refusal puts them back), revokes each consent once the account is gone, from the list read inside that transaction (so a refused deletion revokes none; one the bank will not end is counted in the answer for the holder to end), and removes the account's storage folder. | 2026-10-08 | The dependency audit blocks on what the app ships, and only warns on what only the tooling uses                                                     | A development-only high advisory (`braces`, through ESLint's Next config, no patched release) kept the audit red for days, and six advisories on `next` itself arrived behind the same red unnoticed. `scripts/audit-gate.js` now judges `npm audit --omit=dev` and `npm audit` together: a critical or high advisory in a package the app ships fails, a critical one in the tooling fails, and a high one in the tooling is a warning on every run. | 2026-10-07 | The only administrator cannot delete their own account while other accounts remain; the last account of all can                                     | An instance with accounts and no administrator cannot be administered: nobody can invite, change a role or open a sign-up switch, and the only way back is `AUTH_ALLOWED_EMAILS` or an edit of the database. Deleting one's own account (`POST /api/user/delete-data`) was the one path left to zero administrators, so it now refuses the only administrator, a 409 `last_admin`, while other accounts remain.
